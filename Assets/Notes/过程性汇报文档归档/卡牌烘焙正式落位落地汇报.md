## 1. 执行摘要

本次把“Prefab 动态拼装验证”推进成了正式可复用的烘焙链路：世界空间卡牌现在可以由统一烘焙器把 `CardExample/PlayerCard` 模板烘成单张 Sprite，再由 `Assets/Prefabs/Cards/Card.prefab` 承载显示；卡牌配置编辑器里也补上了“烘焙后预览”。

同时按用户要求补了运行时验证链：`RandomCardPreviewDemo` 现在会在场景里实例化标准 `Card.prefab`，按空格切换不同卡牌，并对怪物数值做动态重烘；`UIChoiceOverlayPanel` 的 `ChoiseButton1` 也能在运行时拿到同一套烘焙产物。

未完全收口的点是：正式奖励/商店/删卡等 ChoiceOverlay 业务数据尚未全面切到这套卡图展示，目前只按需求把 `ChoiseButton1` 做成测试落点；UI 截图通道对 Overlay Canvas 不稳定，因此本次 UI 运行态证据主要通过组件状态核查补足。

## 4. 架构符合性

对照 [ArchitectureDesign.md](../../Assets/Notes/过程性汇报文档归档/ArchitectureDesign.md) 相关章节：

- 表现层不直接改规则数据：世界卡和 UI 只消费 `CardViewData` / `CardDefinition` 构造出来的烘焙输入，没有绕过 Model/System 改运行态。
- 新增逻辑主要落在表现/工具边界：烘焙输入工厂负责把配置和运行态映射为渲染数据，`GameplayWorldPresenter` / `UIChoiceOverlayPanel` 只负责接显示。
- 未向规则层硬塞表现依赖：没有把 Sprite/Prefab 逻辑塞进 Command/System，依旧由 MonoBehaviour 表现层和纯辅助类承接。

## 7. 风险、假设与后续

### 实现假设（待产品/主程确认）

- 当前“标准卡图”统一采用单次烘焙后的大图 Sprite，世界/UI 通过缩放复用；后续若需要分辨率分级，再在 factory 里扩 `Size` 策略即可。
- UI 侧这次只要求 `ChoiseButton1` 做测试，因此没有把帮助奖励/商店/删卡窗口的全部按钮都切到正式业务数据驱动。

### 已知问题 / 技术债

- `UIChoiceOverlayPanel` 的运行态截图在 MCP `ScreenCapture` 通道里不稳定，本次通过组件状态核查补证；若后续要做自动化视觉验收，建议补一条 UI 专用截图路径。
- `Assets/ScriptableObjects/GameConfig/TableNineCardConfig.asset` 当前工作区处于 dirty 状态，本任务没有依赖新增配置内容；质检时请按实际 diff 再判断是否属于本次语义变更。
- 目前 world card 存了 back sprite，但正式战斗表现还没有翻面交互；如后续要做正反切换，可直接在 `CardView` 上继续扩展。

### 对后续任务的建议

- 下一步如果要把奖励/商店等 UI 全部正式切过去，建议复用 `BakedCardRenderDataFactory`，不要在 `UIChoiceOverlayPanel` 里再拼一套图像逻辑。
