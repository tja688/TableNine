## 4. 架构符合性

对照 [ArchitectureDesign.md](ArchitectureDesign.md)：

- **Phase 流转**：清场 → `HelpRewardChoosing` → `RoomChoosing` → `RoomResolving` → 房间子阶段 → `ProceedToNextNode`，与 §5 Flow 一致。
- **RoomChoosing 非阻塞**：`EnterRoomChoosingCommand` 解锁 Overlay，允许帮助卡交互。
- **节点结束延迟结算**：`SettleNodeEndCommand` 仅在 `ChooseRoomCommand` 触发，不在 `PickHelpCardRewardCommand` 提前执行。
- **QFramework 约束**：Command 内架构访问均通过 `this.` 扩展方法。

### 问题摘要

R6 的命令层主流程基本已按新版顺序收束，`ChooseRoomCommand`、`CloseShopCommand`、节点结束结算的落点也基本正确。  
但表现层仍保留旧的“帮助奖励结束后直接进下一节点”提示入口，导致玩家在 `RoomChoosing` 前后可通过 UI 跳过房间选择，这直接违背了 Plan §8 和 `ArchitectureDesign.md` 对 R6 主流程的核心要求。  
由于该问题发生在真实原型 UI 路径，而不是仅限代码内部状态，不能按“小瑕疵”处理归档。  
现有 R6 测试全部通过，只能证明 Command 路径正确，尚未覆盖这条 UI 回退路径，因此汇报中的“原型 UI 能表达完整流程”证据不足。

### 符合项（可保留）

- `CheckClearConditionCommand -> GenerateHelpRewardCommand -> EnterRoomChoosingCommand -> ChooseRoomCommand` 的主命令链路与 Plan §8 基本一致。
- `SettleNodeEndCommand` 把未用帮助卡结算与按快照恢复/移除收束到点击房间之后，符合“不要在帮助奖励阶段提前结算”的要求。
- `RewardConstants.RoomCandidateCount = 2`、金币房 50G、温泉房 +4 上限并回满、商店删卡限制 active 卡等 R6 规则改动均已落地。
- `TableNineR6RewardRoomFlowEditModeTests` 10 条专项测试可作为返工后的回归基础，保留价值高。
