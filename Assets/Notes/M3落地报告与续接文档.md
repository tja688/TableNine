### 二、房间流程详解

```
通关 (ClearReady)
  ├── 选择房间 (ChooseRoomCommand)
  │     ├── 结算未使用帮助卡 (+10/张)
  │     ├── 恢复帮助卡快照
  │     ├── 清空道具栏
  │     └── 根据房间类型：
  │           ├── 金币房 → +30 金币 → 帮助卡 3 选 1
  │           ├── 宝箱房 → 遗物 3 选 1 → (选取后) 帮助卡 3 选 1
  │           ├── 属性房 → 注入属性卡 → 帮助卡 3 选 1
  │           └── 商店房 → 进入商店 → (关闭后) 帮助卡 3 选 1
  ├── 帮助卡选择 (HelpRewardChoosing)
  │     ├── 选取 → 加入卡组
  │     └── 跳过 → +10 金币
  └── 推进节点 (ProceedToNextNodeCommand)
        ├── 节点 +1 ≤ 9 → 开始新节点
        └── 节点 > 9 → Victory
```

### 三、帮助卡快照恢复机制

这是 M3 最核心的逻辑，在 `RewardSystem.RestoreHelpDeckSnapshot()` 中实现：

**时机**：每次 `ChooseRoomCommand` 执行时调用（通关后选房间前恢复）

**算法**：
1. 扫描当前 `HelpCardStates`，收集所有 `IsPermanentlyRemoved=true` 的 UID
2. 扫描 `OwnedHelpCards`，收集节点中新获得的卡（不在快照中的）
3. 遍历快照：
   - 永久移除的卡 → 从 CollectionModel、HelpCardStates、OwnedHelpCards 中**清除**
   - 其余卡 → 重置为干净状态（`IsTemporarilyRemoved=false, IsOnBoard=false, IsInItemSlot=false`）
4. 新获得的卡保持干净状态
5. 清空所有道具栏
6. 发送 `HelpDeckRestoredEvent(restoredCount, permanentRemovedCount, newCardCount)`

**关键保证**：
- 使用药水/飞刀后的永久移除是**跨节点**的
- 节点中获得的新卡（如奖励/宝箱注入）会**保留**
- 快照恢复后所有卡都不在棋盘上、不在道具栏中

### 四、已知限制与后续工作

#### 4.1 场景接入（空着，待场景搭建完成）

当前所有逻辑都是纯 Model/System/Command 层，**没有任何 UI 或场景代码**。需要接入的部分：

1. **房间选择 UI**
   - 监听 `LevelClearReadyEvent` 显示房间选择面板
   - 发送 `ChooseRoomCommand(roomId)` 当玩家点击房间
   - 房间候选从 `RewardSystem.GenerateRoomCandidates()` 获取

2. **帮助卡奖励 UI**
   - 监听 `HelpRewardGeneratedEvent` 显示 3 选 1 面板
   - 玩家选取 → 发送 `PickHelpCardRewardCommand(cardId)`
   - 玩家跳过 → 发送 `SkipHelpRewardCommand()`

3. **宝箱遗物 UI**
   - 监听 `ChestRewardGeneratedEvent` 显示遗物 3 选 1
   - 选取 → `PickRelicRewardCommand(relicId)`
   - 跳过 → `SkipChestRewardCommand()`

4. **商店 UI**
   - 监听 `ShopOpenedEvent` 显示商店面板
   - 购买 → `BuyHelpCardCommand(cardId)`
   - 删除帮助卡 → `DeleteHelpCardForGoldCommand(uid)`
   - 关闭商店 → `CloseShopCommand()`

5. **推进节点**
   - 奖励选择完成后自动或手动发送 `ProceedToNextNodeCommand()`
   - 监听 `NodeAdvancedEvent` 做过渡动画
   - 监听 `Victory` 阶段显示通关画面

#### 4.2 InputLock 机制

- `OpenShopCommand` 会锁定 `OverlayVisible`，关闭时解锁
- `GenerateHelpRewardCommand` 也会锁定 `OverlayVisible`
- UI 层应在 `InputLockReason.OverlayVisible` 激活时屏蔽棋盘点击
- `ChooseRoomCommand` 本身**不加锁**，它依赖后续的奖励/商店命令来加锁

#### 4.3 遗物属性系统

- `RelicSystem.ApplyRelicStats()` 目前只发送 `RelicStatsChangedEvent`
- `StatSystem.GetEffectivePlayerStats()` 需要扩展来查询遗物加成
- 一次性遗物（如凤凰羽毛的免死效果）需要在 `CombatSystem` 中接入触发逻辑
- 荆棘甲的反弹效果也需要在战斗流程中接入

#### 4.4 商店系统增强

- 当前商店只从 4 种基础帮助卡中随机选取
- 后续应根据卡池扩展更多商品
- 商品价格目前使用 `CardDefinition.Price`（药水 30、飞刀 20、宝箱卡 100、属性卡 100）
- 商店删除功能（`DeleteHelpCardForGoldCommand`）需要 UI 支持选择要删除的卡

#### 4.5 导师技能

- `ChooseTutorSkillCommand` 已实现基础逻辑
- 但 `TutorSkillChoosing` 阶段的触发条件和技能池尚未完整设计
- 当前测试未覆盖导师技能的完整流程

#### 4.6 帮助卡奖励质量概率

- 当前 `RewardSystem` 使用硬编码概率：白 65% / 蓝 30% / 金 5% / 红 0%
- `RewardConstants` 中有更详细的宝箱概率配置（普通/蓝/金宝箱）
- 后续可能需要根据层数或难度调整概率

#### 7.2 QFramework 应用合规性

**合格项**：

- 所有 Command 继承 `AbstractCommand`，统一使用 `this.GetModel<T>()`、`this.GetSystem<T>()`、`this.GetUtility<T>()`、`this.SendCommand()`、`this.SendEvent()`，符合 agents.md 第 1 条维护要求（禁止裸调架构能力）。
- 所有 System 继承 `AbstractSystem`，通过 `this.GetModel<T>()` / `this.GetUtility<T>()` 访问下层，未越级访问上层。
- 所有 Model 继承 `AbstractModel`，`ConfigModel.OnInit()` 中通过 `this.GetUtility<IConfigUtility>()` 加载配置，符合 Model → Utility 层级规则。
- Command 无状态：所有 Command 仅通过构造函数传入参数，OnExecute 中不引入额外可变状态。
- 事件驱动：所有状态变更后均 SendEvent，Command 间通过事件解耦。
- TableNine.cs 中 `ExecuteCommand` 拦截正确覆盖 void 和 TResult 两种重载，CommandTrace 日志完整。

**偏差项（需后续修正）**：

1. **`RewardSystem` 中的 `GetAllHelpCardIdsByQuality()` 和 `FilterCandidates()` 为 static 方法**，通过硬编码 ID 列表和 try/catch 跳过不存在的配置，绕过了 `IConfigModel` 的查询接口。这违反了 QFramework "System 通过 `this.GetModel<T>()` 访问数据层"的规范。应改为实例方法，使用 `IConfigModel.GetAllHelpCardDefinitions()` 和 `TryGetCardDefinition()`。
2. **`ShopSystem` 中同样存在 static 辅助方法**（`CountActiveHelpCards`、`CountSameNameCards`），虽不影响功能但破坏了 System 实例方法的统一访问模式。
3. **`RewardModel` 暴露可变 `List<string>`**（如 `HelpRewardCardIds`、`ShopCardIds`），外部可直接修改，破坏了 Model 层封装。建议改为 `IReadOnlyList<string>` 返回只读视图。

##### 7.3.2 已发现的问题（按严重度排序）

**严重（S1）— 影响功能正确性**：

1. **遗物属性加成完全未生效**：`RelicSystem.ApplyRelicStats()` 只发送 `RelicStatsChangedEvent` 空通知，`StatSystem.GetEffectivePlayerStats()` 从未查询 `IPlayerModel.Relics`。结果是获得木盾（DEF+2）、木剑（ATK+2）、木甲（HP+3）等遗物后，玩家有效属性不变。这是 M3 范围内遗物系统的核心功能缺失，报告中虽在 §4.3 提及但未标注为 S1 严重度。
2. **`GoldChangedEvent` 已定义但全代码库从未发送**：所有金币变更（`playerModel.Gold.Value += X`）均为直接赋值，UI 层无法响应金币变化。后续 UI 接入时若不修复，金币面板将显示静态值。
3. **`RewardSystem.GetAllHelpCardIdsByQuality()` 硬编码卡池**：仅包含 4 张帮助卡（Potion/ThrowingKnife/CommonChest/AttributeUp），后续新增的帮助卡（如 Blessing/Bandage 等已定义在 ConfigFactory 中的）不会出现在奖励候选中。`GetAllAvailableHelpCards()` 回退方法进一步遗漏了 `HelpCommonChestId`，两个方法的卡池不一致。

**中等（S2）— 影响健壮性或可维护性**：

4. **`ShopSystem.BuyHelpCard()` 购买后不从 `rewardModel.ShopCardIds` 中移除已购商品**：购买后卡片仍显示在商店列表中，UI 层若不额外处理会导致重复购买尝试（虽因金币/容量检查不会实际成功，但体验不佳）。
5. **多处金币操作硬编码数值而非引用 `RewardConstants`**：`KillMonsterCommand`（第 475 行 `+= 5`）、`SkipHelpRewardCommand`（第 867 行 `+= 10`）、`SkipChestRewardCommand`（第 914 行 `+= 20`）、`DiscardRelic`（第 797 行 `+= 20`）。`RewardConstants` 类定义了这些常量但未被使用，后续策划调值时容易遗漏。
6. **`FilterCandidates()` 和 `CountSameNameCards()` 使用 try/catch 跳过不存在的配置**：应使用 `IConfigModel.TryGetCardDefinition()` 代替异常捕获，这是性能反模式且掩盖潜在配置错误。
7. **`ChooseRoomCommand` 中清空道具栏与 `RestoreHelpDeckSnapshot()` 内部清空道具栏重复执行**：功能无错但属于冗余操作，增加了后续维护的理解成本。
8. **`RelicRuntime` 与 `RelicInstance` 两个遗物运行态类型共存**：`PlayerModel` 使用简化的 `RelicRuntime`（仅 ID + DisplayName + IsConsumed），而 `Data/GameRuntimeData.cs` 中还定义了功能更完整的 `RelicInstance`（含 StatModifiers 等字段）但从未实例化。后续遗物属性接入时需要统一。

**低（S3）— 建议改进**：

9. **`BoardSystem.PlaceCard()` 在格子被占用时抛出 `InvalidOperationException`**：这是代码库中唯一使用异常而非守卫返回的地方，建议改为 `bool` 返回值以保持风格一致。
10. **`RewardContext` 和 `RoomRewardCardId` 枚举已定义但未在任何逻辑中引用**：属于死代码。
11. **`DeckCapacity.ForLayer()` 与 `DeckModel.GetHelpDeckCapacity()` 存在功能重复**：同一逻辑有两种获取路径，后续修改时可能漂移。

#### 7.8 续接开发优先级建议（质检视角）

在续接 AI 开始场景 UI 接入前，建议先按以下顺序修复：

1. **修复 `StatSystem` 遗物属性查询**（S1）：在 `GetEffectivePlayerStats()` 中遍历 `IPlayerModel.Relics`，根据 `RelicDefinition.StatModifiers` 叠加属性。否则 UI 显示遗物无意义。
2. **修复 `GoldChangedEvent` 发送**（S1）：在所有 `playerModel.Gold.Value += X` 的地方改为统一方法或扩展方法，确保每次金币变更都 SendEvent。
3. **修复 `RewardSystem` 硬编码卡池**（S1）：改为调用 `IConfigModel.GetAllHelpCardDefinitions()` 动态获取。
4. **修复 `ShopSystem.BuyHelpCard` 商品移除**（S2）：购买成功后 `rewardModel.ShopCardIds.Remove(cardId)`。
5. **统一使用 `RewardConstants`**（S2）：替换所有硬编码金币数值。
6. **补充导师技能测试和端到端测试**（S2）。

以上修复工作量估计约 2-3 小时，完成后 M3 逻辑层即可视为完整闭环，可安全进入 UI 场景接入阶段。
